Target engine: **PostgreSQL 18** (D9). The design uses `uuidv7()`, `security_invoker` views, `NULLS NOT DISTINCT` and deferrable constraint triggers.

The DDL below is **illustrative**. It defines intent and constraints precisely, and the authoritative version will be the Alembic migrations written in Phases 1–3. RLS policies are listed in doc 09 §4.

## 1. Conventions

| Convention | Rule |
|---|---|
| Primary keys | `uuid`, **UUIDv7 generated by the application** (time-ordered, not enumerable). PostgreSQL 18's native `uuidv7()` is used as the column `DEFAULT` for rows created in SQL (migrations, purge tooling) |
| Tenant column | Every tenant-owned table has `workspace_id uuid NOT NULL` |
| Tenant-safe references | Every parent table has `UNIQUE (workspace_id, id)`. Children reference parents with **composite FKs** `(workspace_id, parent_id)`, so a child cannot point to a parent in another workspace |
| Enumerations | `text` + `CHECK (... IN (...))` (simpler migrations than PG enums) |
| Money | `bigint` whole rupiah. The transaction header `amount` is **positive** (absolute). `transaction_entries.amount` is **signed** (inflow > 0, outflow < 0), and balances are sums of entries (D1, §5.2) |
| Time | `timestamptz` (UTC) for instants; `date` for business dates in the workspace timezone |
| Soft delete | Transactions are **voided** (`status='voided'`, `voided_at`, `voided_by`, set together); accounts and categories are **archived** (`archived_at`). Nothing financial is hard-deleted except by workspace purge |
| Audit columns | `created_at`, `created_by`, `updated_at`, `updated_by` where relevant |
| Optimistic lock | `version int NOT NULL DEFAULT 1` on mutable aggregates |
| Naming | `snake_case`, plural table names |

### 5.2 Transactions and transaction entries (D1, approved)

**Model.** A *transaction* is one logical, user-visible event: a **header** row in `transactions`. Money movement is recorded only in **`transaction_entries`**, one signed row per account affected.

| Type | Entries per revision | Legs | Sign rule | Sum rule |
|---|---|---|---|---|
| `income` | exactly 1 | `single` | `amount > 0` (inflow) | `entry.amount = header.amount` |
| `expense` | exactly 1 | `single` | `amount < 0` (outflow) | `-entry.amount = header.amount` |
| `transfer` | **exactly 2** | `source`, `destination` | source `< 0`, destination `> 0` | **source + destination = 0**; destination = header.amount; the two accounts differ |

*Terminology (D22):* the owner's wording "debit from the source account, credit to the destination account" maps to *source leg negative, destination leg positive*. Code and schema use signed amounts and leg names, never the words debit and credit.

```sql
CREATE TABLE transactions (               -- header: one row per logical transaction
  id                       uuid PRIMARY KEY,
  workspace_id             uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  type                     text NOT NULL CHECK (type IN ('income','expense','transfer')),
  amount                   bigint NOT NULL CHECK (amount > 0 AND amount <= 1000000000000),
                           -- absolute value, integer rupiah; denormalised & verified against entries (INV-3/4)
  txn_date                 date NOT NULL,           -- business date in workspace tz
  category_id              uuid,                     -- income/expense only
  description              text CHECK (char_length(description) <= 500),
  source                   text NOT NULL CHECK (source IN ('text','ai_text','receipt','manual','import')),
  receipt_id               uuid,
  import_ref               text,
  status                   text NOT NULL DEFAULT 'posted' CHECK (status IN ('posted','voided')),
  entry_revision           int  NOT NULL DEFAULT 1 CHECK (entry_revision >= 1),  -- current entry set
  version                  int  NOT NULL DEFAULT 1,                               -- optimistic lock
  replaces_transaction_id  uuid,                     -- D21: set when created by "change type"
  created_by               uuid NOT NULL REFERENCES users(id),
  created_at               timestamptz NOT NULL DEFAULT now(),
  updated_by               uuid REFERENCES users(id),
  updated_at               timestamptz,
  voided_at                timestamptz,
  voided_by                uuid REFERENCES users(id),
  void_reason              text CHECK (char_length(void_reason) <= 200),
  UNIQUE (workspace_id, id),
  UNIQUE (workspace_id, id, type),                   -- target for entries' type-aware FK
  FOREIGN KEY (workspace_id, receipt_id)              REFERENCES receipts(workspace_id, id),
  FOREIGN KEY (workspace_id, replaces_transaction_id) REFERENCES transactions(workspace_id, id),
  -- Category: same workspace AND same kind as type (MATCH SIMPLE → not checked when NULL)
  FOREIGN KEY (workspace_id, category_id, type)       REFERENCES categories(workspace_id, id, kind),
  CHECK ((type = 'transfer') = (category_id IS NULL)),
  CHECK ((status = 'voided') = (voided_at IS NOT NULL)),
  CHECK ((voided_at IS NULL) = (voided_by IS NULL)),
  CHECK ((source = 'import') = (import_ref IS NOT NULL))
);
CREATE UNIQUE INDEX uq_txn_import_ref ON transactions(workspace_id, import_ref) WHERE import_ref IS NOT NULL;
CREATE INDEX ix_txn_ws_date     ON transactions(workspace_id, txn_date)              WHERE status = 'posted';
CREATE INDEX ix_txn_ws_category ON transactions(workspace_id, category_id, txn_date) WHERE status = 'posted';
CREATE INDEX ix_txn_ws_created  ON transactions(workspace_id, created_at DESC);

CREATE TABLE transaction_entries (        -- immutable, append-only money movements
  id                uuid PRIMARY KEY,
  workspace_id      uuid   NOT NULL,
  transaction_id    uuid   NOT NULL,
  transaction_type  text   NOT NULL,       -- copy of header type; pinned by the FK below
  revision          int    NOT NULL CHECK (revision >= 1),
  leg               text   NOT NULL CHECK (leg IN ('single','source','destination')),
  account_id        uuid   NOT NULL,
  amount            bigint NOT NULL CHECK (amount <> 0 AND amount BETWEEN -1000000000000 AND 1000000000000),
  created_by        uuid   NOT NULL REFERENCES users(id),
  created_at        timestamptz NOT NULL DEFAULT now(),
  -- Tenant-scoped FKs: the entry, its transaction and its account are all in ONE workspace
  FOREIGN KEY (workspace_id, transaction_id, transaction_type)
      REFERENCES transactions(workspace_id, id, type) ON DELETE CASCADE,   -- cascade used by purge only
  FOREIGN KEY (workspace_id, account_id) REFERENCES accounts(workspace_id, id),
  -- Shape rules per row:
  CHECK (
       (transaction_type = 'income'   AND leg = 'single'      AND amount > 0)
    OR (transaction_type = 'expense'  AND leg = 'single'      AND amount < 0)
    OR (transaction_type = 'transfer' AND leg = 'source'      AND amount < 0)
    OR (transaction_type = 'transfer' AND leg = 'destination' AND amount > 0)
  ),
  UNIQUE (transaction_id, revision, leg),          -- ≤ 1 single, ≤ 1 source, ≤ 1 destination per revision
  UNIQUE (transaction_id, revision, account_id)    -- transfer legs use two different accounts
);
CREATE INDEX ix_entries_ws_account ON transaction_entries(workspace_id, account_id) INCLUDE (amount, transaction_id, revision);
CREATE INDEX ix_entries_ws_txn     ON transaction_entries(workspace_id, transaction_id, revision);

-- Current (effective) entry set of every transaction; security_invoker so RLS of the caller applies.
CREATE VIEW current_entries WITH (security_invoker = true) AS
SELECT e.*, t.txn_date, t.status, t.category_id
FROM transaction_entries e
JOIN transactions t
  ON t.workspace_id = e.workspace_id AND t.id = e.transaction_id AND e.revision = t.entry_revision;
```

**Triggers (required):**

| Trigger | Fires | Enforces |
|---|---|---|
| `trg_entries_balanced` | CONSTRAINT TRIGGER, **DEFERRABLE INITIALLY DEFERRED**, AFTER INSERT on `transaction_entries` and AFTER INSERT/UPDATE OF `amount, entry_revision, type` on `transactions` | At COMMIT, for each touched transaction, the entry set at `revision = entry_revision` satisfies INV-2…INV-5. No entry set exists with `revision > entry_revision` |
| `trg_entries_immutable` | BEFORE UPDATE OR DELETE on `transaction_entries` | Raises unless `current_user = 'finbot_owner'` (purge). Backed by grants: `finbot_app` has only INSERT and SELECT |
| `trg_txn_type_immutable` | BEFORE UPDATE OF `type` on `transactions` | Raises (D21: type changes go through void + replace) |
| `trg_entries_active_account` | BEFORE INSERT on `transaction_entries` | The account is not archived (new movements only; history keeps archived accounts) |
| `trg_txn_active_category` | BEFORE INSERT/UPDATE OF `category_id` on `transactions` | The category is not archived |

**Invariants** (each one is tested: AT-ENT-* in doc 07):

| ID | Invariant | Enforced by |
|---|---|---|
| INV-1 | Every entry belongs to a transaction and an account **in the same workspace** | Composite FKs |
| INV-2 | Income and expense have exactly 1 `single` entry per current revision; a transfer has exactly 1 `source` + 1 `destination` | Unique (txn, revision, leg) + deferred trigger (minimum count) |
| INV-3 | Sign matches type and leg | Row CHECK |
| INV-4 | `abs(single.amount) = header.amount`; for a transfer, `destination.amount = header.amount` and `source.amount + destination.amount = 0` | Deferred trigger |
| INV-5 | The legs of a transfer use two different accounts | Unique (txn, revision, account) |
| INV-6 | Entries are never updated or deleted by the application | Grants + immutability trigger |
| INV-7 | Across a workspace, Σ amount of current entries of posted transfers = 0 | Follows from INV-4; checked by a property test and a nightly verify job |
| INV-8 | Integer rupiah only (`bigint`); no fractional values exist anywhere in money columns | Types |

**Operation semantics** (each is one database transaction; any failure rolls back everything, so a half-written transfer can never be committed):

| Operation | Header | Entries | Revision row | Audit |
|---|---|---|---|---|
| **Create** (confirm draft) | INSERT `status=posted, entry_revision=1, version=1` | INSERT the revision 1 set (1 or 2 rows) | `create` | `transaction.created` |
| **Edit, non-monetary** (description, date, category) | UPDATE fields, `version+1` | unchanged | `update` | `transaction.updated` |
| **Edit, monetary** (amount, account, source or destination account) | UPDATE `amount`, `entry_revision+1`, `version+1` | INSERT a **new complete set** at the new revision; older sets remain as immutable history | `update` | `transaction.updated` (before/after amounts and account IDs) |
| **Void** (UI "hapus") | UPDATE `status=voided`, `voided_*`, `version+1` | unchanged | `void` | `transaction.voided` |
| **Restore** | UPDATE `status=posted`, clear `voided_*`, `version+1` | unchanged | `restore` | `transaction.restored` |
| **Change type** (D21) | Void the original + INSERT a new header with `replaces_transaction_id` | New set for the new transaction | `void` + `create` | both events |
| **Cancel a draft** | — (drafts never create headers or entries) | — | — | `draft.cancelled` (sampled) |
| **Purge workspace** | Owner role; cascade | Deleted via cascade (owner role only) | — | `workspace.purged` |

Every `UPDATE` on a header uses `WHERE id = :id AND workspace_id = :ws AND version = :expected_version`. Zero rows updated means a concurrent edit, and the user is shown the latest version.

```sql
CREATE TABLE transaction_revisions (
  id              uuid PRIMARY KEY,
  workspace_id    uuid NOT NULL,
  transaction_id  uuid NOT NULL,
  version         int NOT NULL,
  change_kind     text NOT NULL CHECK (change_kind IN ('create','update','void','restore')),
  snapshot        jsonb NOT NULL,          -- header fields + current entry set (structured fields only)
  changed_fields  text[] NOT NULL DEFAULT '{}',
  changed_by      uuid NOT NULL REFERENCES users(id),
  changed_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (transaction_id, version),
  FOREIGN KEY (workspace_id, transaction_id) REFERENCES transactions(workspace_id, id) ON DELETE CASCADE
);
```

### 5.3 Drafts and pending actions

```sql

CREATE TABLE drafts (
  id                   uuid PRIMARY KEY,
  workspace_id         uuid NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,
  user_id              uuid NOT NULL REFERENCES users(id),
  batch_id             uuid,                       -- groups multi-line / receipt drafts
  status               text NOT NULL DEFAULT 'pending'
                       CHECK (status IN ('pending','confirmed','cancelled','expired')),
  proposal             jsonb NOT NULL,             -- validated, resolved proposal (IDs within ws)
  source               text NOT NULL,
  receipt_id           uuid,
  prompt_version       text,
  telegram_chat_id     bigint,
  telegram_message_id  bigint,
  confirmed_txn_id     uuid,
  expires_at           timestamptz NOT NULL,
  created_at           timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (workspace_id, receipt_id)       REFERENCES receipts(workspace_id, id),
  FOREIGN KEY (workspace_id, confirmed_txn_id) REFERENCES transactions(workspace_id, id),
  CHECK ((status = 'confirmed') = (confirmed_txn_id IS NOT NULL))
);
CREATE INDEX ix_drafts_pending ON drafts(expires_at) WHERE status = 'pending';

CREATE TABLE pending_actions (               -- multi-step flows: rename, delete ws, ownership transfer…
  id            uuid PRIMARY KEY,
  workspace_id  uuid REFERENCES workspaces(id) ON DELETE CASCADE,
  user_id       uuid NOT NULL REFERENCES users(id),   -- who may complete it
  kind          text NOT NULL,
  payload       jsonb NOT NULL DEFAULT '{}',
  expires_at    timestamptz NOT NULL,
  completed_at  timestamptz,
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

`drafts.proposal` stores the proposed header and legs (`[{leg, account_id, amount}]`). Its reference IDs (account and category) are re-validated against the workspace at confirm time, and the final INSERTs into `transactions` and `transaction_entries` are protected by the composite FKs and INV-1…INV-5 regardless.

## 7. Balance and report semantics

```sql
-- Account balance as of :as_of (workspace :ws) = opening balance + Σ signed current entries.
SELECT a.id, a.name,
       a.opening_balance + COALESCE(SUM(ce.amount), 0) AS balance
FROM accounts a
LEFT JOIN current_entries ce
  ON  ce.workspace_id = a.workspace_id
  AND ce.account_id   = a.id
  AND ce.status       = 'posted'
  AND ce.txn_date BETWEEN a.opening_date AND :as_of
WHERE a.workspace_id = :ws
GROUP BY a.id;

-- Cash flow for [:from, :to]: headers only; transfers excluded by type.
SELECT t.type, t.category_id, SUM(t.amount) AS total
FROM transactions t
WHERE t.workspace_id = :ws AND t.status = 'posted'
  AND t.type IN ('income','expense')
  AND t.txn_date BETWEEN :from AND :to
GROUP BY t.type, t.category_id;

-- Cash flow by account: current entries of income/expense only.
SELECT ce.account_id,
       SUM(ce.amount) FILTER (WHERE ce.amount > 0) AS inflow,
       -SUM(ce.amount) FILTER (WHERE ce.amount < 0) AS outflow
FROM current_entries ce
WHERE ce.workspace_id = :ws AND ce.status = 'posted'
  AND ce.transaction_type IN ('income','expense')
  AND ce.txn_date BETWEEN :from AND :to
GROUP BY ce.account_id;
```

- **Transfers never count as income or expense.** Every cash-flow query filters `type IN ('income','expense')`. A transfer changes two account balances by +X and −X and leaves the workspace's net worth unchanged (INV-7).
- Voided transactions are excluded through `status = 'posted'`. Older entry revisions are excluded by `current_entries`.
- Entries dated before an account's `opening_date` do not affect its balance. The UI warns when one is entered.
- The MVP computes on the fly. If NFR-PRF-03 is missed, the fallback is an `account_daily_balances` rollup maintained in the same transaction and verified nightly by a recompute (NFR-INT-05).

## 8. Database roles

| Role | Purpose | Privileges |
|---|---|---|
| `finbot_owner` | Owns schema; runs Alembic; purge and prune jobs | DDL; `BYPASSRLS` (FORCE RLS also applies to owners); not used in the bot's request path (doc 09 §4.4) |
| `finbot_app` | Bot and future web runtime | `SELECT, INSERT, UPDATE` on tenant tables; `DELETE` only where hard delete is allowed (drafts, pending_actions, never-used accounts); **`INSERT, SELECT` only on `transaction_entries`, `transaction_revisions` and `audit_events`**; **no** `BYPASSRLS`, no DDL |
| `finbot_backup` | `pg_dump` | `SELECT` on all; `BYPASSRLS` (needed for a complete dump); login only from the backup container |
| `finbot_readonly` | Break-glass support (doc 09 §8) | `SELECT` subject to RLS; disabled by default (`NOLOGIN`) |

## 9. Migration mapping from V1 Google Sheets (D12)

V1 sheet columns: `Date | Amount | Category | Description | User ID | Timestamp`.

| V1 field | V2 target | Rule |
|---|---|---|
| `User ID` | `telegram_identities.telegram_user_id` → `users.id` | Users must be onboarded first, or created by the import with a placeholder display name. An unknown ID without `--create-users` → reject the row |
| (derived) | `workspace_id` | That user's **personal** workspace |
| (derived) | `transaction_entries.account_id` | The personal workspace's "Kas" account (created if missing, with `opening_date` = the earliest imported date, opening balance 0) |
| `Amount` | header `type`, `amount`; one `single` entry | `> 0` → income, entry `+amount`; `< 0` → expense, entry `−amount`; `0`, blank or non-numeric → reject. `amount = round_half_up(abs(x))`, and any rounding difference is reported. V1 had no transfers, so no 2-leg rows are produced |
| `Category` | `category_id` | Case-insensitive match in the matching kind; if none, create it (kind from the type); blank → the default "Lainnya" |
| `Description` | `description` | Trimmed and truncated to 500 characters (reported) |
| `Date` | `txn_date` | Accept `YYYY-MM-DD`, `DD/MM/YYYY`, and a Sheets serial date; otherwise reject |
| `Timestamp` | `created_at` | Interpreted as **UTC** (V1 container ran in UTC; audit B-4) |
| — | `source='import'`, `created_by=user`, `version=1` | |
| row number + hash | `import_ref` | `v1:<sheet_id_hash8>:<sha256(date‖amount‖category‖desc‖uid‖timestamp)[:16]>`. Content-based, so re-runs are idempotent even if rows were reordered. True duplicates (identical content) are reported and imported once unless `--keep-duplicates` |
| — | `transaction_revisions` | One `create` revision per row (`changed_by` = user) |
| — | `audit_events` | One `import.batch_applied` event per user, with counts (not one per row) |

Reconciliation output (`import_batches.stats`): for each user, rows read, imported, rejected by reason, duplicates, rounding adjustments, Σ income, Σ expense, and net. These are compared between the dry run and the apply run (FR-MIG-05).

## 10. Data lifecycle

| Data | Retention | Mechanism |
|---|---|---|
